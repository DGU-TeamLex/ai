## 1. 순수요 = `정상출고량`

**순수요는 `정상출고량` 하나다.** mu/sigma·수요예측·SS/ROP 산출은 모두 이 컬럼에서 출발한다.

| 컬럼 | 채움률 | 판단 |
|---|---|---|
| **정상출고량** | **100.0%** (2024~25 · 2018~19 공통) | **순수요로 사용** |
| 반납입고량 | 96.0% (99.99%가 0) | 반납은 사실상 미발생 → 보정 불필요 |
| 입고량 | 19.5% | 외부 구매 |
| 불출입고량 / 불출출고량 | 각 **0.02%** | 부서간 이동 기록이 거의 없음 → 이중계산 우려 불필요 |
| **자동폐기출고량** | 57.6% | **수요에서 제외** (§2 참조) |

이론적으로 우려되던 부서간 이동 이중계산은 실제 기록률이 0.02%로 무시할 수준이다.

### 자동폐기출고량을 수요에서 빼는 이유

`자동폐기출고량` 은 **재고 수지에 반영되지 않는 별도 정보 컬럼**이다(§2 검증).
이를 소비량에 포함하면 수요가 과대 추정되므로 순수요 산출에서 명시적으로 제외한다.

폐기 실적 자체는 재고유지 비용 계수를 실측 보정하는 데 쓸 수 있으므로,
수요와 분리해 **별도 지표**로 산출한다.

### 음수 `정상출고량` 처리

`정상출고량` 에 음수가 섞여 있다. 반품·정정이 이 컬럼에 역부호로 기록된 것으로 보인다.

**0 으로 절단하고, 절단한 행 수를 품질지표로 남긴다.** 행 자체를 버리지 않는다.

```python
rows["negative_consumption_rows"] = consumption.lt(0).astype("int16")
rows["consumption_qty"] = consumption.clip(lower=0.0)
```

음수를 그대로 합산하면 수요가 상쇄돼 과소 추정되고, 행을 버리면 그 기간의 노출일수가
사라져 mu 분모가 왜곡된다. 절단 + 계수 기록이 둘을 모두 피한다.

### 결측일 처리 — 분모는 달력 노출일수다

원장은 거래가 있는 날만 행이 있는 희소 패널이다(관측 중앙값 11일 / 731일).
따라서 **평균 수요의 분모를 "행이 있는 날"로 잡으면 안 된다.**

- **재고량**은 직전값을 유지(carry-forward)
- **수요 모멘트의 분모는 달력 노출일수** — 재고0 일수와 보유 일수의 합

```python
mu_naive          = demand_total / (zero_stock_days + held_stock_days)   # 달력 기준
mu_available_only = demand_total / held_stock_days                       # 절단보정용
```

이렇게 두면 월별 집계 파케이(`stock_monthly.parquet`)처럼 **행이 없는 기간이 있어도
분모가 줄지 않는다.** 즉 0 채움을 별도로 수행하지 않아도 결과가 동등하다.

분모를 관측일로 잡았을 때의 과대 규모는 실측 **12.77 대 1.95(약 6.5배)** 였다.
이 수치는 잘못된 분모를 쓰면 안 되는 근거로만 쓴다 — 현재 구현은 달력 분모라 해당되지 않는다.

`mu_available_only / mu_naive` 는 `underestimation_factor` 로 보존하고,
품목 단위 Bühlmann 신뢰도 축소(`credibility_k`)의 입력으로 쓴다.

## 2. 재고 항등식

```
마감재고량 = 이전최종재고량
           + (입고량 + 불출입고량 + 반납입고량)
           − (불출출고량 + 정상출고량 + 반품출고량 + 폐기출고량 + 보정출고량)
```

**`자동폐기출고량` 은 이 식에 들어가지 않는다.**

### 검증 결과

정의를 바꾸면 일치율이 크게 달라진다는 점은 두 측정에서 공통이다.

| 항등식 정의 | 2024~25 | 2018~19 |
|---|---|---|
| 자동폐기출고량 **차감** | 96.86% 일치 | 94.24% 일치 |
| **자동폐기출고량 제외** | 거의 전량 일치 | 거의 전량 일치 |

종전에 "항등식 불성립 3.14%(약 51만 행)"를 데이터 품질 문제로 보고했으나,
원인은 데이터 오류가 아니라 **항등식 정의 오류**였다. 원본 데이터 품질은
종전 평가보다 양호하다.

#### 잔여 위반 건수는 아직 확정되지 않았다

두 측정이 어긋난다.

| 측정 주체 | 2024~25 | 2018~19 |
|---|---:|---:|
| 운영 로더 (`stock_preprocessing_report.json`) | **8행** | **39행** |
| 1회성 검증 스크립트 (2026-07-28) | 0행 | 68행 |

**운영 기준은 로더 수치(8 / 39)로 둔다.** 재현 가능한 산출물이 남는 쪽이기 때문이다.
합계 47건은 원본 행·허용오차·파서 제외 기준을 대조할 때까지 미해결로 남긴다
(ai#42). 어느 쪽도 "100% 일치"로 표기하지 않는다.

차이가 날 수 있는 지점 세 가지:

1. **허용오차** — 부동소수 비교 임계값이 양쪽에서 다를 수 있다
2. **파서 제외 기준** — `quotechar` 로 살린 행(§3)의 처리
3. **음수 `정상출고량`** — 절단 전 값으로 항등식을 검증하는지 여부(§1)

### 보조 근거

1. `자동폐기출고량` 은 **음수 499,180 / 양수 11,463** 으로 혼재한다(2024~25).
   실제 출고량이라면 나올 수 없는 분포다.
2. 정의서 v3 에서 **유일하게 컬럼 설명이 공란("-")** 이다 — 정보원 측도 정의를 특정하지 않았다.

## 3. 원본 파싱 주의

물품명·약품명 필드에 줄바꿈이 포함된 행이 있고 큰따옴표로 정상 인용돼 있다.
`split('|')` 로 읽으면 한 논리행이 2~3행으로 쪼개져 컬럼 수 불일치로 버려진다.

```python
csv.reader(f, delimiter="|", quotechar='"')   # 반드시 quotechar 지정
```

실측 유실 규모: 2018~19 **2,744행**, 2024~25 **2,511행**.
`quotechar` 를 지정하면 읽은 행수가 정의서 기재값과 정확히 일치한다
(2018~19 = 6,106,936). 같은 원인이 backend#66 으로 열려 있다.

인코딩은 **UTF-8** 이다(CP949 아님).

## 4. 컬럼 구성 차이 (기간별)

| 기간 | 컬럼 수 | 비고 |
|---|---|---|
| 2024~25 | 18 | |
| 2018~19 | **16** | `구입처코드`·`구입단가` 없음 |

위치 인덱스로 파싱하면 2018~19 가 전량 깨진다. **헤더명으로 매핑**할 것.
`구입처코드`·`구입단가` 는 선택 컬럼으로 두고, 없으면 빈 값으로 채운다.

2020~2023 은 기관이 제공 불가를 확정했다(코로나 시기 변동성). 이 4년 공백은 영구 제약이다.

### 2018~19 를 학습에 쓰는 범위

**전량을 합치지 않는다.** 현재 표준품목과 검증된 규칙으로 매칭된 행만 학습에 넣는다
(정본: `docs/2026-07-29_06_STANDARDIZED_HISTORY_LIGHTGBM_UPDATE.md`).

- strict / core 매칭만 학습 허용 — 이름 단순 fallback 은 감사용으로만 보존
- 기관·부서·내부 물품코드 시계열은 2019 → 2024 를 이어 붙이지 않고
  공백에서 `series_segment_id` 를 새로 끊는다
- 과거 구간의 뉴스·가격·수출입 위험은 소급 연결하지 않는다

즉 이 4년 공백은 **표준품목 축에서만 건너뛰고, 시계열 축에서는 건너뛰지 않는다.**
