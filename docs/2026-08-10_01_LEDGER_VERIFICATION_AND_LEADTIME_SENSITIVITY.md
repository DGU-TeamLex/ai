## 1. 데이터 정합성 — 미해결 논쟁 종결 (`#42`)

### 항등식 잔여 위반 47건의 정체

두 측정이 갈렸던 원인이 **기간별로 서로 달랐습니다.** 양쪽 다 로더가 맞고 제 이전 측정이 틀렸습니다.

| 기간 | 로더 | 제 예전 측정 | 재스캔 | 원인 |
|---|---:|---:|---:|---|
| 2024~25 | **8** | 0 | **8** | 허용오차를 넉넉히 잡아 8건을 놓침 |
| 2018~19 | **39** | 68 | **68 → 39** | 기초재고 결측 29행을 위반으로 오산 |

**부동소수 허용오차** — 0으로 두면 2024~25 는 9,161건, 2018~19 는 10,171건이 잡힙니다. `1e-9` 이상에서는 8 / 68 로 고정됩니다. 허용오차는 `1e-9` 면 충분합니다.

**기초재고 결측** — 2018~19 위반 68행 중 **29행이 `이전최종재고량`·`마감재고량` 모두 NULL** 입니다. `coalesce(...,0)` 로 NULL 을 0 취급하면 입고만 있는 행이 잔차로 튑니다. `68 − 29 = 39` 로 로더 수치와 정확히 일치합니다.

자동폐기 제외 정의도 재확인됐습니다 — 차감하면 2024~25 512,373건 / 2018~19 353,511건이 깨집니다.

### 함께 확정한 수치

| 항목 | 2024~25 | 2018~19 |
|---|---:|---:|
| 정상출고량 음수 | **16건 / −206.0** | 3건 / −8.0 |
| `quotechar` 유실 논리행 | **2,511** | — |
| 행수(csv.reader) | 16,265,602 | 6,106,936 |
| 기관 / 품목 | 3,530 / 17,155 | 1,553 / 11,795 |

정의서 기재값 16,263,091 은 naive split 결과와 같습니다. **실제 논리행은 16,265,602** 입니다(backend#66).

`src.preprocessing` 을 직접 실행한 결과도 기존 기록과 완전히 일치했습니다 — 현재 3,729,983행 / 위반 8행, 과거 1,460,785행 / 위반 39행.

## 2. 튜닝 코드 결함 2건 (`#60`, 커밋 `0c88cda`)

### ① 저장된 파라미터로 결과를 재현할 수 없었음

```python
best_params = {**study.best_params, "n_estimators": selected_n_estimators}
```

`study.best_params` 에는 Optuna 가 **제안한 값만** 들어갑니다. `objective`·`subsample_freq`·`random_state`·`n_jobs`·`force_col_wise`·`verbosity` 가 전부 빠집니다.

LightGBM 기본값이 `subsample_freq=0` 이므로, **저장된 JSON 을 `training.py` 로 옮기면 `subsample=0.79976` 이 적용되지 않습니다.** 보고된 WAPE 가 재현되지 않습니다.

공용 빌더 `build_estimator_params()` 를 두고 tuner·baseline·JSON 복원이 모두 거치게 했습니다. 저장 결과에 `best_params`(전체) / `searched_params`(탐색값) / `fixed_params` 를 분리했습니다.

**추가 발견** — `_baseline_params` 에만 `histogram_pool_size=256` 이 있고 `_suggest_params` 에는 없었습니다. **baseline 과 tuned 가 애초에 동일 조건이 아니었습니다.** 리뷰에서 지적되지 않은 부분입니다.

### ② 외부 신호 게이트에 validation 정보 혼입

`_prepare_folds()` 가 validation 을 포함한 전체 테이블에 게이트를 호출했습니다. fold 를 먼저 만들고 **각 fold 의 train 행으로만** 검사하도록 바꿨습니다.

테스트 5건 추가, **13건 전부 통과**.

## 3. 리드타임 민감도 (`#39`)

기관 요청("값을 바꿔가며 결과가 얼마나 달라지는지")대로 **품목별 차등 없이 전체 일괄 L** 로 산출했습니다. 상세는 `#39` 코멘트에 있고 요약만 옮깁니다.

| L | 보호기간 | 목표재고 합계 | 현행 대비 | 결품률 | 결품수량 | 평균재고 |
|---:|---:|---:|---:|---:|---:|---:|
| 7 | 37일 | 39,883,105 | −17.8% | 35.7% | +9.5% | −6.2% |
| **15** | **45일** | **48,506,479** | **기준** | **33.6%** | **기준** | **기준** |
| 30 | 60일 | 64,675,305 | +33.3% | 30.5% | −4.3% | +10.8% |

**핵심 세 가지**

1. **예측 정확도는 L 과 무관합니다.** 리드타임은 수요예측 모델 입력 피처가 아닙니다(`get_model_feature_columns()`). L 이 바꾸는 건 발주 시점과 결품뿐입니다.
2. **교환비가 비대칭입니다.** L 을 두 배 늘려도 결품은 4.3% 줄고 재고는 10.8% 늘어납니다.
3. **결품의 주원인은 리드타임이 아닙니다.** L 을 4.3배 바꿔도 결품률은 5.2%p 만 움직입니다. 표본의 32%가 재고 0 으로 시작하고 수요발생일 중앙값이 연 10일인 간헐수요라, **초기재고 수준과 수요 간헐성이 지배**합니다.

정기검토 모형(`#54` 확정)에서 목표재고는 `mu×(30+L)×1.2` 로 L 에 선형이라, 검토주기 30일이 완충 역할을 합니다. 연속검토 식은 같은 구간에서 3.1배 뛰므로 **모형 선택이 L 민감도를 2배 바꿉니다.**

## 4. 뉴스 축 — 3층 진단

### ① 뉴스 특성이 0 인 것은 성능 문제가 아니라 산출물 부재

```python
def _merge_risk(feature_table, path, value_columns):
    if not path.exists():
        feature_table[value_columns] = 0.0   # ← 조용히 0
```

`outputs/stock_news_risk_scores.csv` 가 없으면 뉴스 4개 컬럼이 전부 0 이 되고, `_missing_external_signal()` 게이트가 뉴스 모델 2종을 제외합니다.

따라서 **"Module C 포함 41.04% vs 사용량 단독 40.19%" 는 뉴스 없이 나온 비교**이며, 뉴스 무용론의 근거가 될 수 없습니다.

### ② GDELT 는 영문으로 작동합니다

| 질의 | 구간 | 기사 |
|---|---|---:|
| `polypropylene supply` | 2024-01 | **97** (홍해 사태 관련) |
| `polypropylene supply` | 2024-10 | 92 |
| `naphtha price` | 2025-04 | 250 |

**소급 수집이 가능합니다.** 한국어 질의(`sourcelang:kor`)로만 시험했을 때 0건이 나와 "GDELT 불가" 로 판단했던 것은 제 오류입니다. 원자재·공급망은 영문 매체가 1차 소스이고, 모듈 C 가 원자재→HSK→수입 축이므로 영문으로 충분합니다.

※ GDELT DOC API 는 **5초당 1회** 제한이 있습니다. 0건으로 보이는 응답 상당수가 실제로는 레이트 리밋입니다.

### ③ 국내 신호는 뉴스가 아니라 공공 API 가 맞습니다

| 신호 | 소스 |
|---|---|
| 원자재·공급망 | GDELT 영문 (검증됨) |
| 국내 감염병 | 질병관리청 감염병 표본감시 — 질환별×주별 수치 시계열 |
| 리콜·회수 | 식약처 회수정보 (계정 보유) |
| 국내 조달 | 조달청 나라장터 (계정 보유) |

기사는 사건을 늦게·부정확하게 전합니다. 공공 API 는 정확한 날짜와 수치가 붙고, 감염병 표본감시는 **질환별로 갈라져** 품목 연결도 자연스럽습니다.

### 전제 조건 — 메타코드

뉴스 결합 키가 `(year_month, stock_item_key)` 이므로, 뉴스가 유효하려면 **품목별로 갈라져야** 합니다. 전국·월 단위 신호는 519만 행에 24개 값뿐이라 모델이 쓸 것이 없습니다.

품목별로 가르는 것이 `raw_material_meta_code` 입니다. 현재 `item_meta_map` 15,824행이 inventory 품목의 **92.3%** 를 덮습니다. 다만 `#62` 지적대로 **출고량 기준 커버리지는 54.7%** 이므로, 많이 나가는 품목 쪽 구멍을 메우는 것이 뉴스 축의 선결 과제입니다.

## 5. 환경 재현성 — 신규 참여자가 막힐 지점 2건

### `requirements.txt` 의 pandas 상한 부재

`pandas>=2.0` 이라 3.0 도 설치되는데, **pandas 3.0.0 에서 `item_normalization` 이 죽습니다.**

```
AssertionError: 2
  pandas/core/internals/managers.py:2521 make_na_array  assert ncols == 1
```

2.3.3 으로 내리니 통과했습니다. **상한을 `<3.0` 으로 박아야** 합니다.

### macOS SSL 인증서

`fetch` 7개 소스가 전부 `SSL: CERTIFICATE_VERIFY_FAILED` 로 실패했습니다. 인증키 문제가 아니라 **python.org 빌드가 macOS 키체인을 쓰지 않는** 환경 문제입니다.

```
ssl.get_default_verify_paths().cafile  →  None
```

같은 URL 이 curl 로는 됩니다(curl 은 Secure Transport 사용). 해결은 둘 중 하나입니다.

```bash
open "/Applications/Python 3.11/Install Certificates.command"        # 근본
export SSL_CERT_FILE=$(python3 -c 'import certifi;print(certifi.where())')  # 우회
```

README 환경 설정에 넣어두면 좋겠습니다.

### 매핑 중복 51키

`item_alias_to_product_v1.parquet` 505,720행 중 **102행(51키, 0.02%)** 이 같은 `local_item_key` 에 대표품목 2개를 갖습니다.

`standardized_history.py` 는 다른 두 곳(`_read_catalog` L54, `_unique_core_mapping` L277)에서 이미 정렬 후 `drop_duplicates` 로 흡수하는데, `_current_candidates` 만 `raise` 합니다. **같은 파일 안에서 규칙이 일관되지 않아** 기존 방식으로 통일했습니다.

중복의 성격은 셋으로 나뉩니다.

```
① 표기 차이   겐트리손크림_(20g)(신풍제약(주))-20g/개
              겐트리손크림_(12.8mg,0.2g,20mg/20g)(신풍제약(주))-20g/개
② 완전 중복   representative_item_id 까지 동일
③ 별개 제품   IL. HBs-Ab Device / ER.HBs-Ab Device  ← 같은 기관·같은 물품코드
```

**① 은 정규화가 성분 괄호를 흡수하지 못한 것**으로 보여 근본 개선 여지가 있습니다. **③ 은 dedupe 로 덮으면 한쪽이 조용히 사라지므로** 별도 검토가 필요해 보입니다.

## 7. 인프라

**원장 접근 경로 마련** — DAT 2,453MB 를 Parquet 으로 무손실 변환해 **330MB(7.4배 압축)**, 비공개 스토리지에 올렸습니다. 서명 URL 로 다운로드 없이 질의됩니다.

```python
import duckdb
con = duckdb.connect(); con.execute("INSTALL httpfs; LOAD httpfs;")
con.execute("SELECT count(*) FROM read_parquet('<서명URL>')")
```

2,237만 행 전체 스캔 집계가 로컬 0.12초 / 원격 2.0초입니다. 행수·컬럼 무손실 확인했습니다.

**운영 DB 정리** — 354MB → 155MB(199MB 회수). `inventory` 테이블 206MB 중 **빈 공간이 107MB(52%)** 였습니다. 죽은 튜플은 694kB 뿐이라 autovacuum 문제가 아니라, 누적 UPDATE 483만 회 후 수동 VACUUM 이 없었던 탓입니다. 미사용 인덱스 2개 삭제(스캔 6회·10회) + `REINDEX CONCURRENTLY` + `VACUUM FULL` 로 처리했고 API 5종 정상 확인했습니다.
